## On the tenth gate

Mostly sound, and better than it had to be — the SHA re-check at `check-done.mjs:227`
after a server-side `--commit` filter is belt-and-braces done properly, and every failure
mode (`gh` missing, unparseable JSON, run still in progress) fails closed. The holes are
F-16, F-17, F-18.

On the specific scenarios: a **re-run** is handled correctly and the comment at `:230-231`
says so; a **force-push** is caught, because `guard-merge.mjs:110-117` compares the
receipt's head to `HEAD`; a **fork PR** works, because `pull_request` runs are attributed
to the fork's head SHA in the base repo; a **`workflow_dispatch`** run of `ci.yml` would
count, which is acceptable since it runs the same jobs; a run **from a different workflow
file** is rejected on the primary path and accepted on the fallback — F-16.

The fallback is dead code the moment this merges, and dead code in a refusal gate is the
kind that rots unnoticed; it should be deleted after merge, not left for the next `gh`
release to reinterpret.

One thing the gate cannot do and should say it cannot: it validates that *a* `ci.yml` run
was green at that SHA, not that `ci.yml` at that SHA still contains any jobs. A PR that
guts the workflow passes CI and passes gate 10. With `D-43` and no CODEOWNERS, nothing
else catches that either.

## What is good

The `static` job is the right instinct — putting the cheap greps server-side so the local
and remote gates cannot drift is worth more than the greps themselves, and the intent to
copy them verbatim is correct even where the execution slipped (F-23). Gate 10 fails
closed in every branch except the fallback, and the comment at `check-done.mjs:190-197`
explains *why* the SHA pin matters by reference to the guarantee `guard-merge` already
makes, rather than restating what the code does. `.dockerignore` is exemplary: it says
what the build context is, why, and — the part most such files omit — that nothing below
may exclude the two trees the images need. The `images` job is labelled provisional in its
name, its comment names the ticket that inherits it, and "pushes neither" is verifiable by
absence in a file short enough to read. And the PR body's "Not done — must not be lost"
section, including the prediction that the `--workflow` fallback must stop firing after
merge, is exactly the disclosure that makes a review possible.
