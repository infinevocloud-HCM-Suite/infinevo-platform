## The two prior-run findings - confirmed or refuted

### V-1 - migration container never ran Flyway (missing spring-boot-starter-jdbc)

REFUTED as filed, but only after a rebuild. The dependency fix is real: code/backend/migration/pom.xml now declares spring-boot-starter-jdbc alongside flyway-core and flyway-database-postgresql. MigrationApplication.java explicitly excludes DataSourceAutoConfiguration and documents why in a Javadoc comment (Flyway uses its own spring.flyway.url/user/password properties, no shared datasource needed).

First attempt reproduced V-1 exact symptom: docker compose up migrate exited 0 in under a second, logged no Flyway output at all, and flyway_schema_history did not exist (0|NONE). Root cause traced, and it is not a code defect: the local infinevo-migrate Docker image was still the one built 2026-09-17 17:18:44, over an hour before commit ad3f3c6 (2026-09-17 18:34:37) - a stale cached image from the prior verify round, carrying the old application.yml/pom.xml/MigrationApplication.java. Confirmed with docker images infinevo-migrate --format CreatedAt against git log -1 format cd ad3f3c6. After docker compose build migrate (and the rest of the stack) against this commit, rerunning docker compose up migrate produced the full expected Flyway sequence:

    org.flywaydb.core.FlywayExecutor : Database: jdbc:postgresql://postgres:5432/infinevo (PostgreSQL 16.15)
    o.f.c.i.s.JdbcTableSchemaHistory : Schema history table migration.flyway_schema_history does not exist yet
    o.f.core.internal.command.DbValidate : Successfully validated 0 migrations
    o.f.c.i.s.JdbcTableSchemaHistory : Creating Schema History table migration.flyway_schema_history
    o.f.core.internal.command.DbMigrate : Schema migration is up to date. No migration necessary.

and flyway_schema_history existed afterward as exactly 1|migration/migration_user, per section 9 check 3.

Residual risk worth naming, not filed as a new numbered finding: the ticket own section 9 gives no docker compose build step before up migrate or up -d, so a developer or CI runner reusing a volume/image from a prior branch will reproduce V-1 exact symptom silently - exit 0, no error, empty history table looks like nothing to migrate yet rather than Flyway never ran. Section 9 checks 2 and 3 together do catch it (a stale image still passes check 2 but fails check 3 exact-count assertion), so the mechanism itself is sound; the gap is that a rebuild is an unstated precondition, not a defect in the code under test.

### V-2 - FlywayMigrationIT Tests run 10, Skipped 10

CONFIRMED, still open. Tried, in order: DOCKER_HOST=npipe:////./pipe/dockerDesktopLinuxEngine, DOCKER_HOST=npipe:////./pipe/docker_engine (matches the testcontainers.properties NpipeSocketClientProviderStrategy already configured as default), and DOCKER_API_VERSION=1.43 pinned against the daemon actual reported 1.54. All three produce the identical failure: Testcontainers docker-java client gets BadRequestException Status 400 with an empty/zero-valued Info JSON body from both EnvironmentAndSystemPropertyClientProviderStrategy and NpipeSocketClientProviderStrategy, while the Docker CLI itself (docker -H npipe:////./pipe/docker_engine version) talks to the same daemon successfully and reports server 29.5.3. This looks like a docker-java/Testcontainers 1.20.4 vs this Docker Desktop build incompatibility on this machine, not something fixable by environment variables alone. FlywayMigrationIT and DatabasePrivilegesIT both report Tests run 10, Skipped 10 - identical to the prior verify run. This remains a blocker on this machine, not a pass. CI (a Linux runner with a real Docker socket) is the authoritative venue section 9 own footnote names for this; it was not run here.
