## 1. Problem

The frozen Payroll backend has an org-level FBP settings row, and it is a port. What is
wrong with it must not come across.

- **The declaration deadline is a `String`.** `lastDateForFbpDeclaration`
  (`legacy/Payroll-Bend-SBoot/src/main/java/com/itsdev/payroll/entity/claimsanddeclarations/FBP.java:16`)
  — nothing can compare it to today
- **Seven booleans, three of them derived or dead.** `isPayscheduleConfigured` (`:21`)
  duplicates the pay schedule; `isFbpAssociatedWithEmployee` (`:22`) is a count in disguise;
  `isAnyReminderBeforeLockdateEnabled` (`:24`) is "the reminder list is not empty"
- **Reminders are Zoho rows.** `Reminder.java:16-17` carries a 12-digit `reminderId`
  "From Zoho", generated by `FBPServiceImpl.generate12DigitId()` (`:93-97`), and the same
  `reminder` table serves four unrelated parents (`Reminder.java:26-40`)
- **A read writes.** `GET /api/fbp` creates the row with defaults if none exists
  (`FBPServiceImpl.java:39-40,45-72`)
- **No version prefix, hand-built envelope.** `/api/fbp` (`FBPController.java:13`),
  `LinkedHashMap` response (`:26-29`) — DEBT-007, DEBT-008
- **No screen.** The frontend tab is commented out
  (`legacy/Payroll-Fend-react/src/pages/mainPages/allSettingsPages/claimsAndDeclaration/itDeclaration.js:63`)

## 2. Scope

**In scope**

- `payroll.fbp` — one row per tenant: enabled, declaration window, lock, notification flags,
  reminder days
- Read and upsert of that row; explicit lock and unlock
- The list of the tenant's components that are in the plan — the catalogue rows flagged
  `is_fbp_component` (`W-26.1` §6, `earning` and `reimbursement`)

**Out of scope**

- The employee's declaration and its effect on the salary — `W-27.2`
- Sending the release, lock and reminder mails — the flags are stored here; `W-20.1` composes
  and `W-20.2` schedules. See §13, decision 2
- Screens — `W-47`

## 3. Flow

```
[payroll officer] --> [FbpPlanController] --> permission payroll.settings.manage
   --> FbpPlanServiceImpl.upsert --> [payroll.fbp, one row per tenant under RLS]

GET plan       --> the row, or the defaults with exists=false. Never writes
GET components --> W-26.1 earning + reimbursement rows where is_fbp_component and active
```

Permission codes exist: `payroll.settings.manage`
(`code/backend/migration/src/main/resources/db/migration/reference/V020__action.sql:109`),
`payroll.structure.read` (`:111`). No new code.

`isWindowOpen(today)` is true when `is_enabled`, not `is_locked`, and
`window_opens_on <= today <= window_closes_on`. It is the one rule `W-27.2` asks this
service, so the rule lives in one place.

Validation, all `400`: `window_closes_on >= window_opens_on`; both present when
`is_enabled`; every `reminder_days_before_close` entry between 1 and 60, no duplicates.

## 13. Decisions — settled 2026-09-25

| # | Question | Answer |
|---|---|---|
| 1 | Where do the plan's components live? | **On the catalogue, not on the plan.** `W-26.1` already carries `is_fbp_component` on `earning` and `reimbursement`; a second list would drift from it. The plan row holds the window, nothing else |
| 2 | Reminder and release mails? | **Stored, not sent.** `notify_on_release`, `notify_on_lock` and the reminder days are the inputs; `W-20.1` composes, `W-20.2` schedules. A follow-up ticket wires the three events after both land |
| 3 | Default on first read? | **No.** `GET` returns defaults with `exists: false`; only `PUT` writes |
| 4 | Lock as a field on `PUT` or its own call? | **Its own call.** Locking is an event the audit trail (`W-22.1`) should show as one, and the mail hook in decision 2 hangs off it |
